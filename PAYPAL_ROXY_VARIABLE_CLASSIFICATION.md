## High-level flow observed in roxy

The captures show a PayPal checkout and signup/onboarding path, with a later return to Stripe/OpenAI payment pages in the second capture.

Observed navigation path shape:

1. `/agreements/approve?ba_token=BA-<token>` in the second capture.
2. `/pay?ssrt=<ms-timestamp>&token=BA-<token>&ul=1`.
3. `/pay/?...&ctxId=<uuid>&country.x=BR`.
4. `/auth/validatecaptcha` challenge pages in the first capture.
5. `/checkoutweb/signup?...&ba_token=BA-<token>&token=EC-<token>&rcache=1&cookieBannerVariant=hidden`.
6. `/webapps/hermes?...&fromSignupLite=true&fallback=1&reason=<opaque>` in the second capture.
7. `pay.openai.com/c/pay/...?...redirect_pm_type=paypal&redirect_status=failed&ui_mode=custom` in the second capture.

## Classification model

| Class | Meaning | Typical sources | Replay/analysis implication |
| --- | --- | --- | --- |
| Static | Same semantic value across the flow or deployment. | hardcoded query constants, SDK names, API endpoints, static resource URLs. | Can be copied as constants if the target deployment is unchanged. |
| Build/resource static | Stable for a deployed frontend build but changes when PayPal/Stripe deploy. | `_next/static` chunks, `dpl`, hashed assets, `releaseHash`, `contentManifestUrl`. | Treat as deployment-scoped, not permanently static. |
| Page/session dynamic | Created per checkout page, tab, session, or server-side page render. | query params, cookies, inline HTML bootstrap, RSC payloads. | Must be captured/followed from the current flow. |
| Response-derived | Not chosen by the client; returned by server and reused by browser or later requests. | `Set-Cookie`, GraphQL data, response headers, redirect `Location`. | Preserve via browser state or read from responses. |
| User input | Entered or selected by the user; appears in form posts, GraphQL variables, Tealeaf DOM capture. | signup, card, address, phone, OTP, password fields. | Do not hardcode from capture; collect from the user/test case. |
| Device/environment dynamic | Derived from browser, network, screen, timezone, performance, storage, GPU/plugins. | FraudNet/risk, Datadog RUM, Tealeaf, Stripe telemetry. | Generated by runtime environment; values naturally differ per browser. |
| Risk/challenge dynamic | Captcha, bot, fraud, and challenge tokens/timings. | hCaptcha, reCAPTCHA, DataDome, PayPal risk endpoints. | Must be produced by the live challenge/risk SDK for the current session. |
| Third-party SDK dynamic | Generated by Stripe, Datadog, hCaptcha/reCAPTCHA, Google Maps, Google Tag Manager. | third-party requests and beacons. | Owned by SDKs; usually not meaningful outside the current SDK session. |

## Static vs dynamic conclusions

### Safe to treat as static or deployment-scoped static

- Endpoint paths: `/pay`, `/pay/`, `/pay/api/countries`, `/pay/checkout/signup/contact`, `/checkoutweb/signup`, `/webapps/hermes`, `/graphql`, `/idapps/graphql`, `/auth/validatecaptcha`, `/auth/verifyhcaptchapassive`, `/platform/tealeaftarget`, `/xoplatform/logger/api/logger`, `t.paypal.com/ts`, `c.paypal.com/v1/r/d/b/*`.
- SDK/app names and static dimensions: `pgtf=Nodejs`, `env=live`, `s=ci`, `fpti_sdk_name=pa-js`, `product=IWC`, `referrer_tenant=paypal`, many `comp`/`tsrce` string categories.
- Resource URLs and build assets only within the same deployment: `_next/static/chunks/...`, hashed PayPal/Stripe assets, `dpl`, `releaseHash`, `contentManifestUrl`, `x-nextjs-deployment-id`.
- Feature/config flags only for the observed deployment and experiment state: examples include PayPal `feature_flags.*`, Stripe `feature_flags-*`, captcha `reCaptchaEnterpriseEnabled`, `isPolicyBasedChallenge`.

### Must be treated as dynamic for the current session

- PayPal checkout/session tokens: `ba_token`, `token`, `ecToken`, `baToken`, `ctxId`, `clientMetadataId`, `paypal_client_cfci`, `pxpguid`, `csci`, `nsid`, `calc`.
- Challenge/security data: `_csrf`, `_hash`, `_requestId`, `_sessionID`, `jse`, `fn_sync_data`, `grcV3EntToken`, `hcaptchaToken`, `publicKey`, captcha render/eval timestamps, DataDome and Cloudflare bot cookies.
- Browser/device data: viewport, screen, timing, timezone, network effective type, GPU, plugins, JS heap, performance navigation, Tealeaf DOM/event state.
- Server response data: Set-Cookie values, redirect `Location`, GraphQL `authId`/`challengeId`, checkout session data, risk response `ddi/sc/vf`.
- Third-party SDK session IDs and event IDs: Stripe session/log/event IDs, Datadog request/application/action IDs, hCaptcha/reCAPTCHA challenge payloads.

### User-provided and should never be replayed from capture as-is

- Email, password, phone, OTP/PIN, name, date of birth, identity document, card number/CVV/expiry, address fields, geolocation coordinates, and Tealeaf-captured input states.
- This document only records their field names and shapes, not raw values.

## Practical dependency chain

The roxy evidence suggests this dependency chain:

1. Initial PayPal URL provides `ssrt`, `token=BA-<token>`, and `ul`.
2. PayPal page/redirect adds or exposes `ctxId`, `country.x`, locale data, cookies, and page bootstrap variables.
3. HTML bootstrap and JS bundles expose session variables such as `ecToken`, `clientMetadataId`, CSRF, captcha site keys, logger endpoints, FPTI setup, and build metadata.
4. Risk/captcha SDKs generate device, FraudNet, hCaptcha/reCAPTCHA, DataDome, and telemetry values.
5. GraphQL and auth challenge responses return additional state such as checkout session data, locale metadata, 2FA `authId`/`challengeId`, authorize result, and return URL.
6. Redirects to signup/Hermes/Stripe carry the next stage's query variables; the browser also carries response-derived cookies.

Therefore, the main dividing line is: route names, SDK names, and deployment assets are static/deployment-scoped; nearly everything tied to tokens, CSRF, captcha, cookies, telemetry, browser state, user input, or GraphQL response IDs is dynamic and should be captured from the current roxy/browser session.
